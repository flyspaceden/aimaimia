## 1. 目标与业务含义

产业基金从“分配给公司负责人的个人收益账户”改为“由平台保管、按公司记录的应付产业基金”。公司是权益归属及收款主体，公司 OWNER 的个人身份不再参与新账的收款路由。

平台后台能够回答：

- 每一种基金分别收到多少、发生哪些变动、当前余额是多少？每笔钱从哪里来、到哪里去？
- 平台累计为各公司计提了多少产业基金？
- 每家公司有多少处于售后保护期、多少待支付、多少已经公对公支付？
- 每笔计提来自哪个订单、采用什么利润和比例？
- 每笔付款核销了哪些订单的产业基金，对应什么银行凭证？

“留在平台账户”在本系统中表示平台托管记账。计提和账本更新本身不发起银行划拨、不新增实际现金，也不证明银行账户已经隔离存放这些款项。真实付款由平台在银行渠道完成，后台登记并核销。

## 2. 已确认范围

| 项目 | 规则 |
|---|---|
| 新资金归属 | 平台暂存，按公司记账 |
| 收款主体 | 对应公司，不是 OWNER 个人 |
| 个人钱包 | 新计提不得进入个人可用、冻结、提现或抵扣余额 |
| 后台 | 新增产业基金总账及每家公司账本 |
| 各基金逐笔账本 | 每个基金独立展示，每笔入账、冲回及其他余额变动可追溯，不能只有汇总数字 |
| 后续付款 | 平台向公司公对公付款，账本记录支付结果 |
| 历史数据 | 不迁移、不回填、不追缴、不重新计算；原历史流程继续运行 |
| 当前任务 | 设计已确认，按本文实施并验证本地候选 |

本期建议不接入银行自动付款、不增加卖家自助提现、不改变普通/VIP 分润比例，不改变其他分润池、Reward 消费积分、Coupon 平台红包或数字资产的业务规则；其他平台基金增加逐笔账本及审计能力。

## 4. 新旧账切换方案（建议）

建议把“新产生”定义为：**新版本启用后，首次成功执行产业基金计提的分配记录**，以首次处理时持久化的账本版本为准，不按订单创建日期推断。

- 旧产业基金流水、旧分配记录保持原样，继续原解冻、售后和提现流程。
- 已按旧规则分配的订单，重试或补偿仍走旧账，不得再生成新账。
- 启用前下单但尚未计提的订单，启用后首次计提进入新账。
- 新账的账本版本固定为 `COMPANY_LEDGER_V1`；同一订单和分润方案重试不得更换版本。
- 首次路由判断、分配幂等标记和新账计提在同一事务提交；失败整体回滚。
- 发布切换必须暂停旧分润消费者并排空在途事务，再启用新消费者，避免新旧实例同时抢占首次分配。
- 不执行任何对旧 Reward 余额或流水的 UPDATE、搬迁、回填脚本。

实施时先审查现有分配幂等记录，旧分配记录即使没有产业基金流水也不能凭缺失流水重复分配。若需要修复旧异常，另起授权范围。

## 5. 账本结构（建议）

采用独立产业基金模块，以公司为主键维度；不使用个人 `RewardAccount`，也不把新资金重复写入 `PLATFORM` 用户的 Reward 余额。

平台总账由全部公司子账和待归属账汇总，保证只有一份资金事实。公司账反映平台对该公司的应付金额，不代表公司已经收到款项。

### 5.1 建议数据实体

| 实体 | 关键内容 |
|---|---|
| `IndustryFundAccount` | 公司唯一账户、售后冻结额、可支付额、付款预留额、累计计提、累计冲回、累计已支付、已收回款、待追偿额、并发版本 |
| `IndustryFundAccrual` | 唯一来源分配 ID + 公司 ID；订单、普通/VIP 路由、利润基数、比例、公司占比、计算快照、原始金额、剩余各状态金额、账本版本 |
| `IndustryFundLedger` | 不可覆盖的事件流水；计提、释放、冲回、预留、解除预留、付款确认、付款登记冲正、实际回款；关联原流水、订单、付款、操作者和幂等键 |
| `IndustryFundPayment` | 单公司付款单；金额、状态、收款公司名称及对公账户快照、付款账户标识、付款时间、银行流水号、凭证附件、经办人、登记原因 |
| `IndustryFundPaymentItem` | 一笔付款核销哪些计提记录及各自金额，支持部分付款和多订单合并付款 |
| `IndustryFundUnassignedEntry` | 来源公司缺失或无法解析时的平台待归属记录，保留订单、金额、原因及后续归属轨迹 |

账户余额是事务内维护的查询投影，流水是可重建依据。计提源、付款核销关系和审计记录禁止物理删除。公司变更负责人不影响账本；注销或停用公司仍可查询历史，付款需单独验证资格与对公资料。

金额沿用项目 `Float / 元` 存储约定，计算和金额比较先转整数分。产业基金提取、公司分摊的截分和末额补差保持现有规则，避免本次改造引入计价差异。

### 5.2 余额含义与对账

- **售后冻结**：已计提、尚未满足售后释放条件。
- **可支付**：已经释放且未被付款单占用的金额。
- **付款预留**：为待核实的线下付款保留的金额，不可重复付款。
- **累计已支付**：经登记确认的公对公付款金额，记录冲正后按有效记录统计。
- **待追偿**：已实际付款后发生冲回、公司尚未退还的平台应收金额。
- **平台暂存应付**＝售后冻结＋可支付＋付款预留。

总账必须满足（以分核对）：

`累计计提－累计冲回－累计已支付＋实际已收回款 = 售后冻结＋可支付＋付款预留－待追偿`

平台待归属记录单独列示，不能暗中变成平台利润，也不能分给某个 OWNER；与公司账的归属转移必须同事务一减一增且可追溯。第一期可只提供异常查询，归属修复需要明确来源证据。

## 6. 计提与释放

1. 复用普通/VIP 现有利润计算，得到产业基金金额及各公司份额。
2. 依据持久化版本选择旧账或新账。
3. 新账有有效公司 ID 时直接记公司子账，不查询 OWNER。
4. 同一事务创建来源计提和冻结流水，并增加该公司售后冻结额。
5. 定时任务检查订单退货窗口已结束、无进行中售后，并在事务中重新核验订单及售后状态。
6. 满足条件时，从售后冻结转入可支付，同时写释放流水。

公司缺失进入待归属；公司没有活跃负责人但公司身份有效，仍正常计提。零金额不建无意义资金流水，但沿用订单分配幂等标记。

新账任务必须独立于 Reward 冻结任务，避免个人钱包读取到新资金。分页处理使用稳定游标，单项失败记录并可补偿，不能让一批未到期数据持续阻塞后续记录。

## 7. 公对公付款登记（建议）

本期后台管理线下付款过程，不调用银行转账接口。一次付款单只对应一家公司，可以核销多个订单，可以部分付款。

### 7.1 建议流程

`创建付款单并预留金额 → 平台线下公对公转账 → 上传凭证并确认登记 → 核销预留并记录已支付`

创建时验证可支付余额，确定核销明细，保存收款公司名称、对公账号、开户行快照。禁止将个人支付宝、微信或 OWNER 个人账号作为收款资料。公司名称与户名不一致时不允许普通流程直接确认，需线下核实并明确处理规则。

建议状态：

| 状态 | 资金影响 | 可执行操作 |
|---|---|---|
| `RESERVED` 待付款核实 | 可支付转为付款预留 | 登记已付款；核实未付款后取消 |
| `PAID` 已付款登记 | 预留减少，累计已支付增加 | 查看凭证；针对错误登记申请冲正 |
| `CANCELLED` 已取消 | 预留返还可支付 | 只读 |
| `REVERSED` 登记已冲正 | 反向账务记录恢复被错误核销金额 | 只读；原单及凭证保留 |

确认付款必填实际金额、付款时间、付款账户标识、银行流水号、凭证；实际金额必须等于该付款单金额。金额不同应先核实、调整未付款的预留安排，不能覆盖已确认的核销关系。

银行流水号按付款账户建立防重复约束，并使用请求幂等键。重复点击返回原结果，不能再次扣账。网络超时后先查单，不得推断银行付款失败或自动释放预留。

取消仅表示经核实没有真实付款。已真实付款不能靠删除记录或登记冲正假装资金退回；真实退回款应登记独立回款流水及凭证。错误登记的冲正需记录原因、关联原单及审计；已有关联售后或后续处理的付款单应阻止简易冲正，进入异常核对。

首期不开放无来源的手工加减余额。付款预留长期未处理、资料缺失或金额异常应在后台显示待处理事项。

## 8. 售后与冲回（建议，需审阅）

当前代码在退款到账或换货完成后作废整单关联分润。本次建议先保持这个触发和整单口径，仅改变产业基金的归属账务，不顺带引入按退款金额比例重算。

新账冲回表示取消对公司的这部分应付义务；不重复增加实际现金，不再次写入个人或平台 Reward 收入。保留订单、售后 ID、原计提 ID、冲回原因及原始分配快照。

| 产业基金当前状态 | 建议处理 |
|---|---|
| 售后冻结 | 扣减冻结，写冲回 |
| 已释放未预留 | 扣减可支付，写冲回 |
| 已付款预留 | 标记付款单需核实并禁止普通确认；先查清是否已线下付款，再决定取消预留冲回或补登记真实付款后追偿 |
| 已实际支付 | 保留支付事实，冲回公司权益并增加待追偿；不伪造收回款、不自动扣个人钱包 |

付款预留期间发生售后，应立即设置受影响付款单的异常标记并记录待处理事件；不能因人工核实未完成而回滚真实售后成功结果。待核实金额尚未正式冲回前继续列入受限预留，完成核实后幂等冲回。

存在待追偿时建议暂停该公司新付款，提供异常记录与回款登记；后续是否用新产业基金自动抵销需另行确认，本期不自动抵销。

整单冲回是否继续覆盖换货、部分售后，是现有业务规则的明确确认项。本稿不把旧行为解释为用户已经批准的新规则。

## 9. 管理后台页面

### 9.1 产业基金总账

建议在资金管理区域增加“产业基金”入口，沿用 Ant Design / ProTable。

- 汇总：累计计提、累计冲回、平台暂存应付、累计已支付、待追偿；平台待归属金额单列。
- 公司列表：公司编号/名称、售后冻结、可支付、付款预留、已支付、待追偿、最近变动时间。
- 操作：查看公司账本；具备权限时创建付款单。
- 日期筛选明确区分期间发生额和截至所选时间的余额，不将筛选后的流水合计误标成当前余额。

### 9.2 公司账本

展示公司主体信息，不将负责人展示为收款人。分为“计提与变动明细”“公对公付款”“待处理异常”。

计提明细展示来源订单、普通/VIP 类型、利润基数、分配比例、计提金额、冻结/可支付/已核销金额和售后状态。变动明细保留冲回、释放、付款及冲正关联，不通过改写旧流水隐藏历史。

付款详情展示收款公司及对公资料快照、金额、核销订单、银行流水、付款日期、凭证、经办人与状态历史。列表账号脱敏，完整账号和凭证访问需要相应权限。

### 9.3 旧页面兼容

现有公司详情中的产业基金板块改为清楚区分“公司账本（新）”与“历史个人产业基金”。旧 API、旧数据口径保持兼容，新总账不累计旧个人余额。历史页标明“本页为旧规则历史记录，不计入新公司账本”。

页面必须具备加载、空数据、失败重试状态。按钮按权限显示；提交中禁重复点击；错误后保留表单输入。通知及确认弹窗使用 `App.useApp()`。

## 10. API、权限与审计建议

| API（建议命名） | 用途 |
|---|---|
| `GET /admin/industry-funds/summary` | 平台总账 |

| `POST /admin/industry-funds/payments/:id/recoveries` | 登记真实回款，限已关联追偿金额 |

建议区分账本查看、付款登记、登记冲正/回款权限，并接入现有权限目录、管理员 Guard、`@Permission` 与 `@AuditLog`。完整账号和凭证采用受控访问，审计日志不能输出敏感账号全文。凭证使用私有文件或鉴权下载，不能直接暴露永久公开链接。

所有写操作校验公司与来源记录归属、金额大于 0、状态合法、请求幂等；客户端不能自报账户余额或绕过核销明细。

## 11. 一致性要求

- 唯一来源键防重复计提；事件幂等键防重复释放、冲回、核销和回款。
- 计提、余额变动、流水、核销关系必须原子提交。
- 预留/确认/取消/冲回使用 Serializable 事务和状态 CAS，序列化冲突有限重试。
- 新账解冻、售后受理/成功、付款预留/确认必须遵守同一订单和账户锁定顺序；在锁内检查最新售后状态，不能只在事务外读取一次。
- 与外部售后状态变更的可靠衔接采用现有可重试事件机制；若现有机制不足，补充事务性待处理事件，确保资金处理失败可重放且不丢事件。
- 对账检查公司账户投影、不可变流水、计提剩余额及付款核销金额一致；异常阻止受影响账户新付款。
- 多家公司同一 OWNER 仍为独立公司账，负责人更换不得迁移或改变公司余额。

## 12. 验收标准

1. 普通利润 100 元、默认比例 16%：新公司账计提 16 元；个人 Reward 余额及流水均不增加。
2. VIP 利润 100 元、默认比例 10%：计提 10 元；上溯/直推及其他资金池与改造前一致。
3. 两家公司利润占比 60%/40%：普通产业基金分别 9.60 元和 6.40 元，总额守恒。
4. 公司没有 OWNER 仍计入该公司；公司无法识别进入待归属，不成为无来源平台利润。
5. 退货窗口内不能提现/付款；到期且无售后才释放，有活跃售后不释放。
6. 冻结、可支付、预留、已支付各阶段售后均有明确结果；重复事件不重复冲回。
7. 两名管理员并发付款不能超额预留；重复确认只核销一次；重复银行流水被拦截。
8. 支持部分付款及多订单核销；取消预留恢复正确来源余额，已付款记录不能删除。
9. 已付款后冲回产生待追偿，真实回款减少追偿，等式保持成立。
10. 普通管理员无权限不能查看敏感凭证或登记付款，买家/卖家接口不能读取新平台账本。
11. 新版本启用前旧账原值不变，旧解冻/提现/售后仍可运行；新旧版本重试不能双记。
12. 公司更换负责人、停止营业后账本仍可查，新旧账汇总不混算。

实施阶段执行 Prisma validate、后端与管理后台 TypeScript 编译、资金状态机/并发/幂等 API 测试和页面实际渲染验证。上线前还需数据库迁移演练与对账，不以本地测试替代真实银行付款核验。

## 13. 实施与发布边界

设计确认后建议顺序：新增表及独立账本服务 → 分润新旧路由 → 售后与释放 → 付款登记 API → 后台页面 → 对账与测试 → 文档同步。

实施应基于最新 `origin/main` 的干净短期 worktree。原始工作区有大量其他改动，实施已在独立 worktree 中进行，不能将它们一并发布。以当前 AGENTS.md 的 main-based 候选流程为准，不执行旧操作文档中整体合并 staging 的过时步骤。

数据库采用增量迁移，不改写旧 Reward 数据。新账启用后回滚不能仅将旧代码重新上线，否则新计提可能重新进入个人账户；应先暂停新计提和付款写入，保留新账数据与路由标记，采用兼容修复版本恢复。部署、切换时间及回滚步骤在实施阶段写入运维文档。

本地实现、提交与测试状态见实施记录；未推送、未执行线上数据库迁移、测试/生产部署或真实付款。

## 14. 实施采用的细节

用户授权按本文实施后，采用以下建议口径；未来变更另行记录：

1. “新产生”采用第 4 节的首次成功计提口径（包括旧订单尚未计提的情况）。
2. 新公司账暂时沿用整单分润作废触发，包括换货完成；主干已有支付快照和退款兼容逻辑保持不变。
3. 采用“先预留、线下转账、再登记凭证”的付款流程，以及异常已付款冲回后的追偿与暂停付款规则。

## 15. 各平台基金统一账本（追加需求）

### 15.1 账本范围

用户明确要求其他每个基金都建账，每笔记录。根据当前普通/VIP 分润代码，设计统一“基金账本”入口，包含以下独立账本；平台利润虽不是基金，也纳入以完整解释平台侧分配。

| 账本 | 代码类型 | 普通默认比例 | VIP 默认比例 | 归属与明细层级 |
|---|---|---|---|---|
| 产业基金 | `INDUSTRY_FUND` | 16% | 10% | 平台暂存总账 → 公司子账 → 订单与付款流水 |
| 慈善基金 | `CHARITY_FUND` | 8% | 2% | 平台独立账本 → 逐笔来源与变动 |
| 科技基金 | `TECH_FUND` | 8% | 2% | 平台独立账本 → 逐笔来源与变动 |
| 备用金 | `RESERVE_FUND` | 2% | 6% | 平台独立账本 → 逐笔来源与变动 |
| 平台利润 | `PLATFORM_PROFIT` | 49%（主干） | 50% | 平台独立账本 → 订单分配、奖励作废转入等来源 |

比例为本地代码默认值，实际入账记录使用当次配置快照，不用当前配置反推历史。备用金实际金额包含末池补差，必须保存实际金额，不能仅用显示比例重算。

普通奖励、VIP 奖励和直推奖励保留各自已有用户收益账本，不作为平台可支配基金余额相加。分配详情可链接这些奖励记录，帮助核对整次利润分配。

代码还保留旧 `FUND_POOL`、`POINTS` 和 `NORMAL_BROADCAST` 路径。后台设置“历史资金池”只读分类，按原类型展示已有记录，不把旧基金池、积分池改名合并到新慈善或科技基金。如果上线基线仍有遗留路径产生新事件，同样必须逐笔展示，不能遗漏；不借此复活旧业务路由。

除产业基金外，其他基金不按公司建立应付账、不默认向商品卖家公司支付。公司仅作为订单来源筛选维度，不能误示为受益人。

### 15.2 每笔必须记录什么

每笔业务资金事件至少包含以下信息：

| 字段 | 作用 |
|---|---|
| 唯一流水号、事件幂等键 | 防止重复记账、定位单笔 |
| 基金类型、账户维度 | 确认属于哪个基金；产业基金还包括公司 |
| 业务发生时间、记账时间 | 区分事件发生与系统补偿入账 |
| 事件类型 | 计提、冻结、释放、冲回、转入、转出、付款预留、解除预留、付款、登记冲正或回款 |
| 金额、方向及余额分项变化 | 区分资金增减与冻结/预留的内部状态变化 |
| 变动后余额 | 查看该事件后的可用、冻结及预留余额；不只显示当前余额 |
| 来源订单、分配记录、售后/付款单 ID | 从账本进入原业务证据 |
| 普通/VIP/历史路径、规则版本 | 解释采用哪套规则 |
| 利润基数、实际比例、分配快照 | 解释计算依据；非计提事件关联原计提，不伪造分配比例 |
| 对方账户/基金或收款主体 | 转账、付款、冲回时说明资金去向 |
| 原流水、关联流水及原因 | 将冲回、冲正与原始事件串起来 |
| 系统任务或管理员及凭证 | 说明由谁、因为什么产生这笔变化 |

不能仅改变账户余额而不写流水。状态从冻结变为可用时，也要有可追溯事件，但这类内部转移不计为第二次基金收入。平台内部基金间转移必须有成对关联记录，汇总时不能重复计为外部收入或支出。

已发生流水不覆盖、不删除。错误用反向事件冲正。历史数据缺少当时余额或配置快照时，显示“历史未记录”，不能用今天的余额或规则补造历史事实。

### 15.3 存储与写入方案

**产业基金**按第 5 节的新公司账本方案实现；**其他平台基金**继续以已有平台 `RewardAccount/RewardLedger` 为资金事实源，扩展必要事件记录与查询投影。不能再建立一套可独立增减的基金余额与原账户同时记钱。

建议增加通用 `PlatformFundEvent` 审计事件模型，关联来源 Reward 流水和分配记录，存储事件类型、发生额、各余额分项增减、变动后余额、账户内序号、幂等键和业务引用。它是原账户的事务性审计记录，不是第二个资金账户。

- 原有 Reward 账户/流水变更与审计事件同事务提交，任何一步失败整体回滚。
- 每个账户的余额变更在锁定后分配单调递增事件序号，避免同一时间戳下的流水顺序和历史余额不确定。
- 对账使用各余额分项的增减合计，不把冻结转可用当作净收入。
- 统一读模型对产业基金读取新账本事件，对其他基金读取关联审计事件；原 Reward 流水仅作为来源链接，不能与对应事件重复列为两笔入账。
- 无审计事件的旧 Reward 流水只读展示，标记历史来源，不迁移或回填。新旧列表分页使用稳定来源标识和游标，避免重复或漏项。
- 实施前列出所有能写平台基金账户的入口，包括普通/VIP 分割、旧路径、售后归平台、奖励过期/作废及现有调账，逐个接入，不只改两处分割函数。

其他基金的原始入账时点与售后处理规则保持原样：当前平台分割直接记可用余额，不套用产业基金售后冻结和公司待支付模型。若需修改其他基金的可用时点，应另行确认。

### 15.4 历史边界与余额展示

沿用不迁移、不回填历史资金的方向。其他基金已有余额仍然是真实账面余额，不能因为新账本启用而清零，也不能将历史余额当成新收入。

建议启用逐笔审计时，在停写或账户锁定条件下保存只读期初余额与切换序号，不产生资金流水、不改变任何旧余额。新账本使用“期初余额 + 启用后净变动 = 当前余额”对账。历史查询直接读取已有记录，无法从旧数据证明的状态变化不补造。

产业基金新公司账从 0 开始，历史个人账户及历史平台兜底产业基金继续单列，不进入新公司应付总额。平台总览必须标明哪些包含期初余额、哪些是新账，不混用口径。

### 15.5 后台展示

统一入口建议为“资金管理 → 基金账本”。

1. **总览**：每种基金一行，显示期初余额、期间收入、期间支出/冲回、当前余额及最后变动时间；产业基金额外显示公司应付、冻结、预留、已支付及待追偿。
2. **基金详情**：余额概览和逐笔流水，支持日期、普通/VIP、订单号、来源公司、事件类型筛选。每行显示金额方向、变动原因与变动后余额。
3. **流水详情**：展开计算快照、来源订单和关联冲回/付款记录；来源缺失应明确提示。
4. **产业基金**：从基金详情进入公司列表、公司子账和公对公付款流程，保留第 9 节的设计。
5. **历史资金池**：只读展示旧路径与旧产业基金记录，与新账分区。

普通/VIP 是同一基金的来源维度，不额外建立两份可花余额。总览区分平台自有资金与公司应付产业基金；禁止把公司待付款与平台利润简单合计为“平台可支配余额”。

### 15.6 查询 API 与权限补充

建议新增 `GET /admin/fund-ledgers/summary`、`GET /admin/fund-ledgers/:fundType/entries`、`GET /admin/fund-ledgers/:fundType/entries/:id`，明确账本版本、期初/期间/期末口径及分页字段。产业基金公司与付款 API 仍按第 10 节。

统一账本配置独立查看权限；增加查看页面不等于获得其他基金付款或调账权限。其他基金本期不因“有账本”自动新增转出、跨基金调拨或自由调整余额的按钮。未来开放用途支出时必须沿用逐笔、凭证和对账规则，具体业务流程另行设计。

### 15.7 新增验收

- 五类账本独立可查，每笔新资金或余额状态变动有事件，无“只改余额不留痕”的写入口。
- 普通/VIP 同基金可分组筛选，比例和金额取实际分配快照，补差可解释。
- 售后归平台等非订单计提收入可追溯到原奖励及订单，不被误标为新利润计提。
- 基金间关联事件可核对，净汇总不重复计算内部转移；未授权的跨基金转出不可执行。
- 同账户并发写入后，账户内序号及每笔变动后余额连续，余额可由期初和事件重建。
- 新事件与旧 Reward 来源不重复展示，历史缺失快照不伪造，历史余额不清零。
- 各基金总览与详情在一致快照下汇总一致；失败重试、重复事件、权限和分页均验证。

实施顺序相应扩展为：平台基金写入口审计 → 通用事件与读模型 → 产业基金公司子账和新旧路由 → 售后/释放/付款 → 统一后台 → 对账验收。本地实现以本节范围为准，验收状态记录在配套实施记录。
