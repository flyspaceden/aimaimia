# 资金管理三页拆分与操作体验设计

> 2026-09-09 · 用户已批准设计，三页业务实现已完成；测试与部署进度见下方实施记录。
> 用户已确认三个独立页面：基金账本、公司产业基金、公对公付款。
> 基于已部署基金功能设计，沿用现有管理后台视觉与账务规则。原型使用明确标识的示例数据，不连接业务接口。

## 1. 设计目标

让财务人员快速完成三件事：找到一笔资金、看懂归属与状态、在正确的入口处理付款或更正。每个页面保持一个主体列表，不再把所有列表纵向堆叠。

不另加第四个“资金驾驶舱”。当前任务是提高查找和处理效率，不增加新的统计概念。

## 2. 视觉与布局决策

- 沿用管理蓝 `#1E40AF`、深蓝侧栏 `#001529`，白色工作区 `#FFFFFF`、浅灰背景 `#F5F5F5`、正文 `#1F2937`、细边界 `#E5E7EB`。警示橙、错误红仅用于明确异常。
- 沿用系统中文字体，页面标题 24px、分组标题 16px、表格与表单 14px、说明 12px；金额使用等宽数字并右对齐。
- 页边距 24px；搜索操作区与列表在同一白色工作区内。常用摘要放在一条紧凑信息栏，减少大卡片。
- 列表行高约 52px；表头与右侧操作列固定；主要对象名称左对齐。
- 详情抽屉用于快速查阅；复杂记录支持进入已有独立详情页并保留来源列表上下文。
- 操作反馈只回应用户操作，不做自动数字跳动、滚动动画或装饰性渐变。

审视原方案后，取消“六张大统计卡 + 多个列表”的布局，改为摘要栏、搜索区、单一主表。这里最重要的视觉强调是公司可支付金额和待处理状态。

## 3. 导航与路由

```text
资金管理
├─ 基金账本             /fund-ledgers
├─ 公司产业基金         /fund-ledgers/companies
└─ 公对公付款           /fund-ledgers/payments
```

保留现有基金流水、流水详情、公司详情、付款详情 URL。静态列表路由放在 `/:fundType` 前，防止 companies/payments 被当成基金类型。

每个入口独立按权限显示。公司页的“登记付款”跳转付款页并带上公司条件；付款页点击公司名称返回公司子账。跳转回列表时恢复搜索、筛选、排序、页码和滚动位置。

## 4. 基金账本：回答这笔钱从哪里来、到哪里去

### 页面结构

```text
基金账本                          [刷新]
[当前基金] [历史账本]
[基金名称搜索]                  [查询] [重置]
[记账期间：本月]                 [更多筛选]
已选条件：本月 ×
基金名称 | 期初 | 期间收入 | 期间支出/冲回 | 当前余额 | 查看流水
```

- 主列表默认展示产业基金、慈善基金、科技基金、备用金、平台利润。
- 旧基金池、积分池及旧平台产业基金归入“历史账本”，不与新公司应付合算。
- 不展示把公司应付和平台利润相加的“总可支配余额”。
- 日期默认“全部已记录期间”；“本月”是可选快捷条件，不能默认隐藏历史又让用户误以为没有数据。
- 期初与期间发生额随日期条件变化，当前余额始终标为当前值；查询早于账本启用期时，无法证明的期初显示“未记录”。

### 流水查找与查看

点击“查看流水”打开对应基金流水页：关键词搜索明确支持流水号、订单编号；常用筛选为记账时间、收入/支出/状态变动、普通/VIP 来源。公司名称筛选使用搜索选择框，不要求用户记住内部 ID。

默认列：时间、事件、来源订单、变动金额、变动后余额、操作。冻结、预留、追偿分项放在展开内容或列设置中，不默认铺成十几列。

点击流水先打开详情抽屉，顺序为“金额与事件 → 来源订单/公司 → 计算依据 → 余额变化 → 关联记录”。计算依据用“利润基数 × 实际比例 = 计提金额”解释；必要补差单列，不能用当前配置反推旧账。内部 JSON 不作为日常主要展示。

基金及流水不提供直接编辑金额或删除按钮。

## 5. 公司产业基金：回答欠哪家公司、哪些能处理

### 页面结构

```text
公司产业基金
当前筛选公司：可支付 ¥…    付款预留 ¥…    待追偿 ¥…
[公司账本] [待归属]
[全部] [有可支付金额] [有待核实付款] [有待追偿]
[搜索公司名称]             [更多筛选] [查询] [重置]
公司 | 可支付 | 售后冻结 | 付款预留 | 待追偿 | 最近变动 | 查看 / 登记付款
```

摘要明确是“当前筛选公司合计”，与列表同一筛选范围；若服务端暂不支持筛选汇总，则标注“全部公司合计”，不得假装联动。

公司列表不放订单日期筛选。高级筛选可包含公司状态、可支付金额范围、最近记账时间；这些都是拟补充的查询能力，不是现有 API 已经完整支持。

### 公司详情

点击“查看”打开公司子账，页头只放公司名称、当前状态和当前余额，不用空白字段展示并不存在的“公司编号/银行档案”。

详情包含三个标签：

1. **资金明细**：该公司的计提、冻结释放、冲回及余额变化，可按订单和时间查询。
2. **付款记录**：该公司付款单，点击进入付款详情；无需再次搜索公司。
3. **待处理事项**：待核实付款、待追偿金额，带明确处理入口。

存在待追偿时，“登记付款”显示不可用及原因，不把失败留到提交后。没有余额或公司状态不允许付款时同样说明原因。不存在新账的公司显示“尚未产生新产业基金”，避免普通空数据变成错误页。

### 待归属

只在公司页内使用标签，不再增加侧栏页面。展示来源订单、原计提、已冲回、待归属净额、原因和时间，默认只看未处理记录。历史记录可切换查看。

本次仅提供查看来源和变化记录。没有证据归属流程前，不新增“随便选择一家公司划入”的编辑按钮。

## 6. 公对公付款：处理付款单，不在这里改账本

### 页面结构

```text
公对公付款                              [新建付款单]
待付款核实 n 笔 · ¥…       需核实 n 笔       待追偿 n 笔
[全部] [待付款核实] [需核实] [已登记付款] [已取消] [已冲正]
[公司名称 / 付款单号 / 银行流水号]          [查询] [重置]
[创建时间]                  [更多筛选：付款时间、金额、经办人]
付款单 | 公司 | 金额 | 状态 | 创建/付款时间 | 操作
```

“需核实”是 `needsReview` 的业务筛选，不新增重复的付款状态。数量和金额使用与列表一致的范围。默认以待处理优先作为可见快捷入口，进入页面仍显示“全部”，避免误以为其他记录丢失。

银行卡信息、凭证、核销订单不全部铺在主表；进入详情查看。银行流水搜索仅向有付款/回款权限的人开放，不让查询成为敏感信息旁路。

### 查看详情

宽抽屉或独立详情页按以下顺序组织：

- 顶部：付款单、公司、金额、状态和此时允许的主要操作。
- 收款资料：户名、开户行、账号；普通只读权限只看脱敏信息。
- 核销明细：本单包含哪些来源订单，各核销多少；可展开原计提。
- 付款与回款凭证：付款时间、银行流水、附件、回款记录。
- 操作历史：经办人、时间、原因和状态变化，按时间线展示。

### 新建付款单

使用较宽的侧边表单，分三组：

1. **选择公司与金额**：支持公司名称搜索，展示可支付余额；从公司页进入时预选公司，用户可返回公司账核对。
2. **核对对公资料**：户名按公司主体校验；开户行和账号填写。可设计“沿用上次资料”作为显式选择，不能静默沿用旧账号；本次不另建银行账户档案系统。
3. **登记原因与确认摘要**：提交前可见公司、金额、收款信息及“建立付款单并预留余额”的明确结果。

主要按钮命名“创建并预留”，不使用含糊的“确定”。成功后进入新付款单详情并刷新原列表和余额；请求结果未知时先查原单，保留幂等键和输入，不鼓励重复创建。

### 编辑与状态规则

| 状态 | 允许的操作 | 页面表达 |
|---|---|---|
| 创建前的表单 | 修改公司、金额、收款资料、原因 | 所有可编辑项集中在创建表单；离开有输入时提示未保存 |
| 待付款核实，尚未实际转账 | 查看、确认已付款、核实后取消 | 不直接覆盖已经预留的金额与收款快照 |
| 待付款核实，资料填错 | 更正未付款单 | 引导核实未转账 → 取消旧单 → 带入原资料创建新单；不是原地修改历史 |
| 需核实 | 查看来源、说明实际付款事实 | 必须明确“已付款”或“未付款”；已有真实付款不能当作取消处理 |
| 已登记付款 | 查看凭证；符合条件时更正错误登记/登记实际回款 | 不显示普通“编辑金额”；冲正与真实回款是不同操作 |
| 已取消 / 已冲正 | 查看历史；允许时沿用资料新建 | 原记录只读 |

“更正未付款单”是建议的前端引导，底层仍复用取消和创建两个已存在操作。必须显示两步结果：取消成功但新建失败时保留“旧单已取消，新单未创建”的状态，允许重试新建，不宣称原子替换。

不新增付款后任意改金额、补写假凭证或删除金融记录的能力。

## 7. 三页统一的搜索与操作体验

- 搜索框占主要宽度，输入提示明确可搜字段；中文名称模糊搜索，订单/付款/银行流水按完整编号精确匹配优先。输入后按回车或“查询”提交。
- 常用筛选直接显示，低频条件放“更多筛选”；应用后用可移除标签展示，不让隐藏条件造成查不到数据。
- “重置”清除关键词与筛选并回到第一页；“刷新”保持条件。改变筛选重置页码，排序不丢条件。
- 查询条件放 URL，标签、日期、排序、页码可恢复；关键词和日期切换采用 latest-request-wins，旧响应不能覆盖新结果。
- 详情关闭保留列表位置；提交成功只刷新相关数据，保持筛选；空页总数变化时安全回到有效页码。
- 列表默认每页 20 条，可选 50/100；行内最多两个常用操作，其余进“更多”。不提供批量确认付款/批量冲正。
- 无结果：显示具体筛选条件和“清除筛选”；接口失败：保留条件并给“重试”；空公司账：解释新账从首次计提开始。
- 不把加载中或请求失败显示成余额 0；未知历史数据显示“未记录”。
- 普通查看、付款登记、冲正/回款按现有权限分离，菜单、按钮和 API 一致。无操作权限时仅查看；业务条件不满足时显示禁用原因。
- 1280px 桌面优先保证主表可读；窄屏隐藏低频列并可横向滚动，不挤压金额和主操作。抽屉在窄屏变为全屏。

## 8. 与现有能力的对应

| 能力 | 现状 | 本设计处理 |
|---|---|---|
| 各基金流水与详情 | 已有路由/API | 复用，改善列密度和可读计算依据 |
| 公司账/付款详情 | 已有路由/API | 复用，拆出列表与明确跨页入口 |
| 公司名称搜索、日期/状态基础筛选 | 已有部分能力 | 对齐三个页面范围，保留当前余额/期间发生额区别 |
| 付款单号/银行流水统一搜索 | 当前查询不完整 | 实施时补充 DTO 与服务过滤，不能只画输入框 |
| 金额范围、经办人筛选 | 当前不完整 | 优先级低于基本三页拆分，作为后续增强；无接口时不展示伪筛选 |
| 筛选后的数量/金额汇总 | 当前有全局汇总 | 补充同范围统计或明确标注全局；避免错报 |
| 更正未付款单 | 已有取消/创建，未封装引导 | 复用操作并处理分步失败，不改账务状态机 |
| 收款银行档案编辑 | 没有独立已确认需求 | 不在本次扩展 |
| 导出、收藏视图、批量付款 | 非当前已确认功能 | 本轮不加入默认交付 |

优先落地三页拆分、真实可用的基础搜索、详情上下文、按状态操作和反馈。高级金额/经办人筛选作为后续选项，不把页面改造扩大成新财务系统。

## 9. 原型与后续验收

原型：`docs/ui-prototypes/fund-management-v2/index.html`，支持菜单切换、关键词搜索、状态筛选、查看抽屉、公司到付款的跳转，以及创建表单内修改资料。样例数据仅保存在页面内存，刷新即恢复。

原型是视觉和交互提案，不能代表搜索 API、权限校验、金额核销已经实现。确认设计后另起实施提交；本次不发布到 staging-next。

实施验收重点：三页入口清楚、列表查询真实有效、返回列表不丢条件、单权限用户可查看对应详情、状态不允许的操作不可执行、重复点击/超时不重复创建，以及桌面/窄屏可用。保留既有资金与退款回归门禁。


### 原型检查记录

已检查桌面与 390px 窄屏截图、公司关键词查询、付款状态筛选和创建表单的公司/户名/可支付余额联动。窄屏收起低频列，把操作集中到详情，保证金额完整显示。原型中的确认已付款流程停留在预览说明，不提交真实付款或业务记录。


## 8. 本次实施范围与验证

已实现三个权限独立入口、主列表搜索/状态/日期及 URL 分页、公司和流水详情抽屉、付款预览、远程公司选择、未付款单取消后重建，以及未知响应保留原输入/幂等键。公司摘要由服务端按同一筛选计算；付款摘要按公司、关键词、日期范围计算各待处理视图数量。列表采用服务端固定最近变动/创建时间倒序，不新增自定义排序，金额/经办人高级筛选仍留作后续。

本次不调整资金核心、历史数据或数据库结构。根代理审核后修正了详情路由、付款更正参数传递、银行流水筛选契约与 5xx 未知结果处理。查询、权限与资金流程由隔离 PostgreSQL 回归覆盖；页面由独立 Playwright fixture 覆盖查询保留、只读权限、预选公司、完整详情跳转、未知请求重试、取消成功创建失败后的续建及窄屏布局。最终发布记录追加到运维文档。


### 独立审查收口

根代理逐条核验独立审查意见，修复付款详情未知响应保护、表格流水号链接缺失基金类型、旧 `search` 书签清除，以及窄屏抽屉宽度限制。新增与详情付款动作都在提交中禁改字段；未知时冻结完整请求，避免改键后重复记录。全部改动继续使用原有资金 API，无新增资金写入接口。

CI 首轮页面测试发现浏览器服务继承 `NODE_ENV=test`，组件库的 DOM ID 进入 mock 模式；测试服务固定为 development，并在连续筛选操作间断言前一步已更新 URL 与表单，重跑验证，不跳过用例。

发布复验进一步确认快速筛选并非仅测试等待问题：重置已更新 history，但下一次点击可能仍调用旧渲染捕获的 `searchParams`。查询更新改从浏览器当前地址合并，确定性同帧双点击测试在旧实现失败、修正后连续三轮通过。窄屏几何断言等待入场动画并允许 0.01px 亚像素误差，同时验证左右边界与宽度。

线上页面验收补充：待归属默认 PENDING 查询存在 PostgreSQL enum=text 的 42883 错误，改为对绑定参数显式转换为数据库枚举，不改字段或数据。新增真实 PG 覆盖空/非空、PENDING/RESOLVED/ALL、全额冲回排除及审计事件，再由 HTTP 路由验证返回 200。总览返回筛选也补齐回归。
