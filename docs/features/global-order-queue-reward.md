# 全平台订单队列奖励

> 状态：代码审查与自动化验证收口，待 Staging 迁移和灰度验证（2026-07-28）
> 边界：这是独立的队列奖励规则，不修改普通树、VIP 树或直推奖励；对外仍按“队列、树、直推”三部分介绍。

## 一句话规则

所有普通商品订单共用一条平台队列。订单确认收货时按商品净实付金额生成位置，并在平台内部计算该单利润的配置比例如何分给前面的有效位置；来源订单和受益位置订单都过售后期且都没有成功售后后，红包才直接进入可提现余额。

## 固定业务边界

- 平台只有一条队列，不按商户、普通/VIP 身份或商品分类拆队列。
- 普通用户和 VIP 用户全部参加；同一用户重复购买会产生新位置，也允许奖励自己的历史位置。
- 只处理普通商品订单；VIP 礼包继续走原有规则。
- 队列奖励从该订单原本的平台利润分成扣除，不增加订单总支出；实际未分出的预算仍归平台。
- 普通树、VIP 树、直推奖励照常计算，队列使用独立账户、流水、配置、状态和接口。
- 只有“缺少成本”时仍生成位置且本单队列出资为 0；订单金额守恒失败等其他利润核对异常必须停止入队和推进，并保留告警。

## 后台参数

| 参数 | 默认值 | 约束 |
|---|---:|---|
| 新订单入队开关 | 关闭 | 关闭后不接收新订单，已有内部待结算记录继续处理 |
| 每轮人数 `N` | 21 | 2–100；每个位置观察后续 `N-1` 个位置 |
| 利润奖励比例 | 1% | 1%–100%，且启用时不能超过普通/VIP 平台利润比例并必须通过统一利润安全校验 |
| 拆单金额单元 | ¥200 | 正数；只按完整单元拆分 |
| 单笔订单位置上限 | 100 | 1–500；防止异常小拆单单元造成单事务无限扩张 |
| 分配方式 | 平均 | 平均 / 可重放的正态随机 |
| 正态标准差 | 0.25 | 0–1 |
| 随机最小/最大倍数 | 0.5 / 1.5 | 0.01–10，最小不得大于最大 |
| 生效时间 | 空 | 关闭时可为空；开启时前后端都强制必须选择，早于生效时间付款的订单不补入 |

每笔订单在付款时保存当时的队列规则快照，后续修改参数只影响新付款订单。

## 金额与位置

1. 商品净实付金额不含运费，并已经扣除平台红包、消费积分和 VIP 折扣。
2. 商品净实付必须大于 0；大于 0 时位置数为 `min(单笔位置上限, max(1, floor(商品净实付 ÷ 拆单单元)))`，纯奖品/零实付订单不入队。
3. 队列名义预算为 `min(订单利润 × 奖励比例, 该订单平台利润分成)`，全程按整数分计算。
4. 多位置共享同一物理订单的收取上限；该订单内部待结算与已到账队列红包之和不得超过商品净实付。
5. `N` 是硬滑动窗口：每个新位置只奖励并推进全局 FIFO 最前面的 `N-1` 个历史位置。大单可一次产生多于一个窗口的位置，但超出窗口的后续位置排队等待，不会让下一单向所有积压位置同时发奖。
6. 同一物理订单拆出的多个位置互不奖励、互不推进，但每个位置都会依次奖励并推进当时窗口内的历史位置；同一用户其他历史订单的位置仍可领取。因暖场、封顶或不足 1 分无法发出的部分留在平台。
7. 正态随机只改变个人份额，不改变本单可分总额、收取上限或资金守恒；相同种子可审计重放。

## 内部待结算、到账与售后

- 确认收货时只生成平台内部待结算记录，不创建用户钱包冻结流水，也不向用户展示“冻结红包”。
- 队列红包实际到账后可以提现；用户发起提现时，处理中金额沿用现有钱包冻结字段展示，这不是售后期内的待结算红包。
- 每个订单的奖励保护截止时间覆盖无理由退换货天数、普通质量退换货天数和生鲜质量退换货小时数三者中的最长窗口；单笔红包再取来源订单与受益位置订单截止时间的较晚者。任一时间缺失时不自动释放。
- 任一侧存在进行中售后时继续留在内部待结算。
- 两侧均为已收货、售后期均已结束、没有进行中或成功售后时，才原子创建 `AVAILABLE` 钱包流水并进入统一提现。
- 任一侧退款、退货或换货成功时，该订单作为“奖励来源”发出的红包和作为“受益位置”收到的红包都作废。受益侧作废的已回收金额全额回平台；来源侧按累计退款后仍保留的利润比例回平台，多次部分退款使用累计目标减已回流金额的幂等调整流水，不能重复记利润。
- 已到账红包若已提现或正在提现，不阻断售后成功：当前余额先回收；提现处理中金额与追偿记录关联，付款失败退回时优先偿还追偿，付款成功则保留可审计欠款；钱包、队列状态页和提现校验均按“队列账户余额－未偿追偿”展示/校验净可提现额，不能反复提现逃逸。
- 售后被驳回、取消或关闭，不视为成功售后；在其余条件满足后正常释放。

## 用户提醒

- 每一笔实际大于 0 且最终通过双边售后检查的队列分配，在进入 `AVAILABLE` 时生成一条持久化“排队红包到账”消息，不把多笔合成一笔。
- App 在前台按“创建时间 + 消息 ID”稳定游标分页追赶新消息，成功播放一笔才推进一笔游标；同一消息只响一次。首次启用从服务端最后一条已存在消息建立基线，不依赖设备本地时钟；用户已软删除的消息不会被铃声接口重新取回。
- 售后成功而作废的内部待结算记录从未进入钱包，因此不发到账消息。

## 示例与边界

下表均假设 `N=21`、拆单单元 `¥200`；金额仅用于解释规则。

| 场景 | 结果 |
|---|---|
| 第 1 个位置进入 | 前面无人，不发红包；预算留平台；位置开始等待后续 20 个位置 |
| 第 2 个位置进入 | 本位置预算全部分给第 1 个有效位置 |
| 第 21 个位置进入 | 给前面仍有效的最多 20 个位置分配；第 1 个位置观察满 20 次后出队 |
| 第 22 个位置进入 | 第 2 个位置观察满 20 次后出队；窗口继续滑动 |
| 当前只有 5 个前序位置 | 预算在这 5 个有效位置中分，不虚构第 6–20 人 |
| 同一用户连续购买 | 新位置可以奖励该用户自己仍在队列中的历史位置 |
| 订单净实付 ¥0 / 纯奖品单 | 不入队，不产生位置 |
| 订单净实付 ¥80 | 不足 ¥200，但实付大于 0，仍生成 1 个位置 |
| 订单净实付 ¥200 / ¥399 | 都生成 1 个位置 |
| 订单净实付 ¥400 / ¥450 | 都生成 2 个位置；同一物理订单的两个位置共享 ¥400 / ¥450 上限，彼此不奖励、不推进 |
| 订单净实付 ¥600 | 生成 3 个位置；利润和奖励预算按整数分拆到 3 个单位，尾差进最后一个单位 |
| 订单净实付 ¥6000 | 默认生成 30 个同订单位置；全部保留，前 20 个先进入硬窗口，后 10 个按 FIFO 等待；下一位置只奖励并推进窗口内最多 20 个位置 |
| 拆单参数异常小 | 最多生成后台设置的单笔位置上限，避免资金事务失控 |
| 平均分配 2 分给 4 人 | 只有 2 人各得 1 分；尾分按可重放轮换顺序处理 |
| 正态随机 | 每人金额可不同，但所有红包加平台留存严格等于本单预算 |
| 某订单快达到收取上限 | 先补到上限，剩余预算继续分给其他未封顶订单 |
| 所有人都封顶 | 不再给他们发新红包；无法发出的预算留平台，位置仍按观察次数正常出队 |
| 前序位置用户已封禁/注销 | 当次不入账，预算在其他有效位置间重分；该位置仍推进观察次数，避免卡住队列 |
| 缺少商品成本 | 订单正常产生位置，但本单出资 0，不生成虚假红包 |
| 功能关闭 / 付款早于生效时间 | 不入新队列，也不追补历史订单 |
| 确认收货后无售后 | 只留内部待结算记录；两侧售后期都结束后直接到账 |
| 来源订单正在售后 | 继续内部待结算，不进入钱包 |
| 受益位置订单正在售后 | 同样继续内部待结算 |
| 任一侧退款/退货/换货成功 | 相关内部记录作废；该售后订单自己的队列位置同时作废 |
| 连续两次部分退款 | 每次按累计剩余利润重算平台应回流总额，只记“新目标－已回流”的差额 |
| 到账后正在提现又发生售后 | 售后不回滚；提现失败的冻结款先偿还追偿，提现成功则保留欠款并锁住等额后续队列可提现余额 |
| 售后驳回/取消/关闭 | 不作废；售后期和其他条件满足后正常释放 |
| 重复确认收货 / Cron 重跑 | 幂等返回原结果，不重复建位置、不重复入账、不重复响铃 |
| 同时大量确认收货 | Serializable 事务 + 全局队列锁串行确定顺序，冲突最多重试 3 次 |
