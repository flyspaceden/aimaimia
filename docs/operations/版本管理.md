> **本文专注于"环境清单"**（域名 / 数据库 / 服务名等实物对照）。
> **分支策略与切换时机** → `docs/operations/branch-strategy.md`
> **具体 git 命令** → `docs/operations/github操作.md`

## 一、三个版本概览

| 版本 | 实际载体 | 用途 | 谁在用 |
|------|---------|------|--------|
| **开发版本** | 你的 Mac（`localhost:3000`，跑 `npm run start:dev`）| 日常写代码、调试 | 开发者本人 |
| **测试版本** | `test-*.ai-maimai.com`（部署已批准的 `staging` 候选）| 功能验证、回归、真机测试 | 开发者 + 测试人员 + 测试包用户 |
| **上线版本** | `*.ai-maimai.com`（代码来自 `main`，生产部署需手动 approval）| 真实用户使用 | 全部对外用户 |

**关键**：开发版**不需要单独 GitHub 分支**。本地就是开发层——你在哪个分支签出的代码，本地跑的就是哪个版本。

## 二、GitHub 分支结构

```
origin/main                         生产代码唯一真相源
  ├─ codex/* / feature/*            从最新 main 建立的短期开发候选
  ├─ hotfix/*                       从最新 main 建立的生产紧急修复
  └─ origin/staging                 当前测试 release train；发布后必须向 main 收敛
archive/* / tag                     分支重建前的不可变保护点
delivery/staging                    当前旧 Delivery 工作的独立保留 lane
```

**铁律**：
- 永远不直接在 main、staging 或固定微信测试目录写代码。
- `main` 是唯一长期基线；`staging` 只承载明确的测试候选，不是第二个开发主干。
- 所有 feature/candidate 都从最新 `origin/main` 建立；一个逻辑改动一个 commit。
- 合并 main、部署生产、执行 migration、上传小程序和发布 App 是彼此独立的门禁，不能互相冒充完成。
- hotfix 必须同步到 staging 和仍活跃的候选分支；发布后审计双向差异。
- 当前旧 staging 含独立 Delivery，禁止整体 merge 或覆盖；按 `branch-strategy.md §五` 一次性无损收敛。

完整的分支策略、典型场景、切换时机判断、应急情况见 **`docs/operations/branch-strategy.md`**。

具体的 `git` 命令、自动部署触发规则见 **`docs/operations/github操作.md`**。

### 提交信息规范（CLAUDE.md 强制流程 #10）

```
fix(scope): 描述           例：fix(auth/forgot-password): 忘记密码后失效 session
feat(scope): 描述           例：feat(reward): 消费积分双轨实施
update(scope): 描述         例：update(app): 优化商品列表加载速度
docs(scope): 描述           例：docs(operations): 重写 staging-to-production
chore(scope): 描述          例：chore(deps): 升级 prisma 至 5.9.0
```

**一个 commit 一个逻辑改动**，禁止把不相关改动塞一起（线上出事才能只 revert 一项）。

## 四、GitHub Actions 部署规则

### 部署规则

| 触发方式 | 结果 |
|---------|----------------|
| `staging` | 按路径自动部署测试环境（test-*.ai-maimai.com） |
| `main` push | **不自动部署生产**；仅更新生产代码分支并运行对应 CI |
| `main` + workflow_dispatch + production approval | 手动部署生产环境（*.ai-maimai.com），并锁定 exact SHA |

### 部署什么

| 改动目录 | staging 部署到 | main 部署到 |
|---------|---------------|------------|
| `website/` | — | ai-maimai.com |
| `admin/` | test-admin.ai-maimai.com | admin.ai-maimai.com |
| `seller/` | test-seller.ai-maimai.com | seller.ai-maimai.com |
| `backend/` | test-api.ai-maimai.com | api.ai-maimai.com |

## 五、App 版本管理

App 不部署到服务器，通过应用商店分发。但通过切换 API 地址区分环境。

### 三个阶段

#### 1. 开发阶段

```bash
# 启动 Expo 开发服务器
npx expo start
```

- 手机装 **Expo Go**，扫码实时预览
- App 连接 `http://localhost:3000`（本地后端）
- 改一行代码，手机上立刻更新

#### 2. 测试阶段

打**测试包**安装到手机：

| 平台 | 分发方式 | 说明 |
|------|---------|------|
| iPhone | TestFlight | 苹果官方测试分发，邀请测试人员安装 |
| Android | APK 直接安装 | 或通过蒲公英 / fir.im 分发给测试人员 |

- 测试包连接 `https://test-api.ai-maimai.com`
- 使用测试数据库，不影响正式环境
- 可以邀请多人同时测试

#### 3. 上线阶段

提交到应用商店审核：

| 平台 | 提交到 | 审核时间 |
|------|--------|---------|
| iPhone | App Store Connect | 1-3 天 |
| Android | 华为/小米/应用宝等 | 1-5 天 |

- 上线包连接 `https://api.ai-maimai.com`
- 使用正式数据库

### App 环境切换

App 内通过环境变量自动切换 API 地址：

```
开发模式 → http://localhost:3000/api/v1
测试包   → https://test-api.ai-maimai.com/api/v1
正式包   → https://api.ai-maimai.com/api/v1
```

## 六、版本号规范

### App 版本号

格式：`主版本.次版本.修订号`，例如 `1.2.3`

| 部分 | 什么时候升 | 例子 |
|------|-----------|------|
| 主版本 | 大改版、不兼容的更新 | 1.0.0 → 2.0.0 |
| 次版本 | 新增功能 | 1.0.0 → 1.1.0 |
| 修订号 | 修复 Bug | 1.0.0 → 1.0.1 |

### 后端 API 版本

API 路径已包含版本号：`/api/v1/...`

如果 API 有不兼容的改动，新增 `/api/v2/...`，旧版本保留一段时间。

## 七、完整工作流程示例

### 场景：开发“商品评价”功能

1. `fetch` 远端，在短期干净 worktree 中从最新 `origin/main` 建立 `feature/product-review`。
2. 按实际受影响范围修改 App/小程序/后端/后台；只改小程序时不得顺带改 App。
3. 本地门禁通过后创建 Draft PR，审查文件清单、CI、安全与回退路径。
4. 只把本轮批准候选送到 staging，记录部署 SHA，并完成浏览器/测试包/微信真机验证。
5. 保留已测试 commit 历史进入 main；main 更新后手动触发 exact-SHA production workflow。
6. 核对线上 SHA、migration、health 和业务探针；App 和小程序仍分别走 EAS/App Store 与微信体验版/审核/发布。
7. 将 main 已发布修复同步回 staging，审计双向差异；未发布功能继续保存在独立 feature 分支。

## 八、版本回退

上线后发现严重问题，需要立即回退到之前的版本。

### 网站/管理后台/卖家中心回退

生产静态站点回退仍需经过审查和手动 production approval，不能把 `main` push 当成自动上线。

```bash
# 1. 查看最近的提交记录，找到要回退到的版本
git log --oneline -10

# 输出示例：
# a1b2c3d fix: 修复支付bug（← 有问题的版本）
# e4f5g6h feat: 新增评价功能（← 要回退到这里）
# h7i8j9k update: 优化首页

# 2. 回退到指定版本（用新提交的方式，不丢失历史）
git revert a1b2c3d
git push origin <reviewed-hotfix-branch>
# → PR/CI 通过后，手动部署新的 exact SHA

# 多提交或 merge commit 回退必须先列出准确提交和 mainline，逐项生成 revert；
# 不使用容易漏掉起始提交的范围快捷命令。
```

### 后端 API 回退（分钟级）

```bash
# 方法一：代码层 git revert，重新经过 PR/CI，再手动发布 exact SHA
# 方法二：按 production runbook 切回 deploy-backend-versioned.sh 保留的旧版本目录，
#         恢复旧 cwd/entrypoint 并验证 PM2、health 和业务探针
```

#### 数据库回退

Prisma `migrate resolve --rolled-back` **不会撤销已经执行的 DDL 或恢复数据**，不得把它当成生产回退命令。每次 migration 发布前必须准备并验证：精确候选 SHA、生产备份、克隆库迁移演练、向后兼容窗口，以及按该 migration 编写的反向 SQL 或整库恢复方案。生产失败时先停止写入并按已批准 runbook 执行；没有可验证恢复点时不得冒险修改 migration 状态表。

### App 回退（最慢，需要审核）

App 回退是最复杂的，因为已经发布到应用商店的版本无法直接撤回。

| 方案 | 操作 | 时间 |
|------|------|------|
| **发布修复版本** | 修复 Bug → 打新包 → 提交审核 | 1-5 天 |
| **服务端降级** | 后端 API 做兼容处理，让旧版本正常工作 | 几分钟 |
| **强制更新提示** | App 内弹窗提示用户更新到修复版本 | 依赖用户操作 |

**最佳实践：** App 上线前充分测试，因为回退成本最高。如果出问题，优先通过后端 API 做兼容处理，同时提交修复版本审核。

### 快速回退命令速查

```bash
# ═══ 查看历史 ═══
git log --oneline -10              # 查看最近 10 次提交
git log --oneline --graph          # 图形化查看分支历史

# ═══ 回退单个提交（代码层，推荐） ═══
git revert <commit-id>             # 撤销某次提交的改动
git push origin <reviewed-branch>  # 重新经过 PR/CI；生产仍需手动部署

# ═══ 临时切回旧版本查看（不修改任何东西） ═══
git checkout <commit-id>           # 查看旧版本代码
git checkout main                  # 切回最新版本
```

### 回退决策流程

```
发现线上问题
    │
    ├── 影响小，可以等？
    │       → 从最新 main 建 hotfix/feature → staging 测试 → main → 手动生产部署
    │
    ├── 影响大，需要立即处理？
    │       → git revert 或旧版本产物 → CI → production approval → exact-SHA 手动回退
    │
    └── 数据库也改了？
            → 停止写入 → 按已验证反向 SQL 或备份恢复方案处理 → 复验数据与 migration
```

## 九、注意事项

1. **永远不要直接在 main、staging 或固定微信测试目录写代码**，所有开发从最新 `origin/main` 建短期干净 worktree
2. **测试环境和生产环境数据库完全隔离**，测试不会影响真实用户
3. **上线前必须在 staging 测试通过**，并证明进入 main 的提交与已测试候选一致
4. **.env 文件不提交到 GitHub**，每个环境有各自的配置
5. **数据库操作要谨慎**，生产库的增删改需要备份后再执行
6. **App 发布需要时间**，应用商店审核 1-5 天，提前规划
