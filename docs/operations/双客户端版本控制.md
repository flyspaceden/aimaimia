# 爱买买 — App 与微信小程序双客户端版本控制协议

> **状态：强制执行。** 本文覆盖所有会影响 `app/`、`miniapp/`、共享 `backend/` API/数据契约的改动。开发只能在临时 worktree 完成；微信开发者工具只使用一个固定、只读式同步的 staging 测试目录。

> **目的：** 把“Git 源码版本、测试后端部署版本、App 构建/OTA 版本、微信开发者工具编译产物、预览/真机二维码”明确分开，任何一个都不得代替另一个。

## 一、不可突破的规则

1. **一个测试只认一个源码身份。** 每次 App 或小程序测试记录必须同时包含：`SOURCE_SHA`、绝对 `SOURCE_PATH`、目标环境（local/staging/production）和构建时间。只有截图、二维码、网页或“刚刚编译成功”不构成版本证据。
2. **脏目录禁止进入发布链路。** `git status --short` 非空时，不得在该目录 `pull`、切分支、导入微信开发者工具、编译、预览、真机调试、提交或推送。不得用复制文件、覆盖目录、`reset --hard` 处理这种状态。
3. **远端最新 staging 是测试基线。** 每次开始小程序/App 测试或发布前先 `git fetch origin staging`；当前 HEAD 必须包含最新 `origin/staging`。落后或分叉时，新建干净 worktree，不在旧目录补丁式同步。
4. **App 与 miniapp 是独立客户端。** 改动必须在任务记录中明确 `app=是/否`、`miniapp=是/否`、`backend=是/否`。共享 API 变更须分别验证受影响的两个客户端；一个端通过不代表另一个端已通过。
5. **一个逻辑改动一个提交。** 同一功能跨 App、小程序、后端时，可有多个 scope 清晰的提交；不得把历史遗留、本机配置、生成物和业务改动混入同一提交。
6. **只有用户授权才推送。** 本地验证、提交不等于 staging 部署、App OTA、微信体验版或真机验收。推送、部署、OTA、上传、支付等状态必须逐项如实报告。

## 二、受控工作区

### 2.1 创建与识别

从远端测试基线创建工作区，示例：

```bash
git fetch origin staging
git worktree add -b codex/<scope>-YYYYMMDD \
  /absolute/path/to/.worktrees/<scope>-YYYYMMDD origin/staging
cd /absolute/path/to/.worktrees/<scope>-YYYYMMDD
git status --short
git rev-list --left-right --count HEAD...origin/staging
```

开始前必须满足：状态为空，且落后数为 `0`。若需要继续一个尚未合并的 feature 分支，应从该 feature 的已知提交新建 worktree，并在测试/合并前 rebase 或 merge 最新 `origin/staging`；不能把根目录或旧 clone 当作发布源。

### 2.2 固定测试目录与本机配置

- 固定测试目录是 `/Users/jamesheden/Desktop/农脉 - AI赋能农业电商平台-staging`，简称 `STAGING_TEST_CHECKOUT`。它固定停留在 `staging` 分支，**不是开发目录**：不得直接编辑、提交、切换功能分支或从其中推送。
- 微信开发者工具长期只导入 `$STAGING_TEST_CHECKOUT/miniapp`；不得在一次测试周期内切换到其他 clone、仓库根目录或开发 worktree。这样开发者工具的项目路径始终不变。
- 每次 staging 推送和 CI/deploy 成功后，必须从干净的开发 worktree 执行 `node scripts/sync-staging-test-checkout.mjs`。该脚本仅允许固定目录从 `origin/staging` **快进**，随后执行 `npm ci`、`verify:release-context` 和 `build:staging`；目录脏、分叉或分支错误时会拒绝操作，绝不覆盖或 reset。
- 若固定目录出现本地改动，先将改动整理为独立恢复分支，再恢复 `staging` 分支并快进；不得直接 `pull`、强推、覆盖、stash 或 reset。
- `node_modules/`、`dist/`、`.runtime-audit/` 和微信开发者工具缓存不是源码版本证据。
- `miniapp/project.config.json` 是共享工程配置，必须保持 Git 受控、可复现。仅属于个人设备的选择写在 `miniapp/project.private.config.json` 或工具自身配置；若开发者工具反复改写受控文件，先把可共享默认值规范化提交，再继续测试。
- 不得同时让两个目录作为同一个小程序的“当前测试版本”。一个测试周期只能指定一个绝对 `miniapp/` 路径。

## 三、小程序强制流程

### 3.1 编码前与提交前

1. 在 `plan.md` 写明受影响系统、目标测试环境和最小验收路径。
2. 从干净 worktree 修改代码；每完成小程序前端任务，同步更新 `docs/architecture/frontend.md` 和 `plan.md`。
3. 代码审查必须核对：小程序 DTO/Repo 与后端契约、分包/路由、登录态、支付/资金状态、`dist` 产物及新增 API 的 feature flag。
4. 提交前运行 `git diff --check`，并按逻辑范围暂存；禁止 `git add -A` 把无关改动带入。

### 3.2 本地质量门

在候选提交完成后，从该 worktree 的 `miniapp/` 目录依次执行：

```bash
npm ci
npm run verify:release-context
npm run verify
# 为微信开发者工具保留 staging 产物，最后再执行一次
npm run build:staging
```

`npm run verify:release-context` 会拒绝脏工作区和落后/分叉的 staging 基线。`npm run verify` 覆盖 lint、TypeScript、测试、staging/production 构建和生产产物校验；其通过不等于微信开发者工具或真实后端验收。

### 3.3 微信开发者工具与真机

1. 导入的只能是固定 `$STAGING_TEST_CHECKOUT/miniapp`，不得选择仓库根目录或开发 worktree。
2. 在“详情”核对 `projectpath` 与记录的 `SOURCE_PATH` 一致；终端执行 `git log -1 --oneline`，记录 `SOURCE_SHA`。
3. 运行 `npm run build:staging` 后，在开发者工具点击“编译”。界面仍是旧页面时，先确认 `dist/` 的 SHA 对应和 AppService 是否重载；禁止凭旧预览二维码声称已测试新代码。
4. “编译”只验证本机运行；“预览”生成临时体验二维码；“真机调试”增加设备调试通道。三个动作都不等于上传审核版或正式发布。源码有新提交后，旧二维码立即失去“当前代码”资格。
5. 真机用例记录功能路径、账号类型、后端环境、结果和截图。涉及支付、提现、退款、库存或配送/自提状态机，必须在获授权的测试数据和测试环境闭环，禁止用本地成功替代。

## 四、App 强制流程

1. 同样从干净且包含最新 `origin/staging` 的 worktree 开始；不得与小程序共用“脏根目录”作为测试源。小程序的固定测试目录不用于 App 开发或 EAS 发布。
2. 在任务记录中注明 App 是本次变更的受影响端还是仅做兼容回归端。
3. App 的源码提交、staging 测试包、EAS OTA、TestFlight/App Store 构建是四个不同状态。每次报告必须写明实际完成到哪一步，不能以 Git push 代替 OTA/构建，更不能以 EAS 构建代替真机验收。
4. 共享后端合同有变化时，以同一 `SOURCE_SHA` 对应 staging 后端进行 App 回归；发布主线仍遵从 `docs/operations/app-发布与OTA手册.md`。

## 五、推送、部署和回退

### 5.1 staging 推送

在用户明确授权后，先复核：

```bash
git fetch origin staging
git rev-list --left-right --count HEAD...origin/staging
git diff --check origin/staging...HEAD
```

仅当远端落后数为 `0`、差异范围已审查、提交和验证证据完整时，才可快进推送。推送后必须报告 SHA、改动的客户端、是否触发后端/后台自动部署，以及尚未完成的外部验收。

### 5.2 shared backend 规则

- 修改 `backend/`、数据库迁移、环境开关或 API 合同时，staging push 可能触发测试后端部署；必须等待 CI/deploy 真实成功后，才可测试依赖该 API 的 App/小程序。
- 不得把“前端已编译”描述成后端已部署，也不得把“API 可访问”描述成 feature flag、测试点位和迁移已就绪。
- 生产推送、真实支付、真实提现、迁移回退均须单独用户授权。

### 5.3 回退

- 每次测试记录保留 `SOURCE_SHA`。回退优先用 `git revert <SHA>` 生成新的可审查提交；除非用户明确授权，禁止强推、改写远端历史或在业务目录执行破坏性 reset。
- 小程序出现旧界面时，先判定是 `SOURCE_PATH`、`dist`、开发者工具 AppService、二维码还是后端环境不一致；不要先修改业务代码。
